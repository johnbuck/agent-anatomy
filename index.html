A field guide

Agent Anatomy

A visual tour of what makes a modern AI agent tick — head to toe, one part at a time.

Meet the agent

An AI agent isn't one thing — it's a body of parts wired together. Below: each piece, mapped onto a body you already understand. The rest of this guide takes them one tab at a time.

Where to next

Each tab in this guide unpacks one part of the body — the brain (Models), what fits in mind right now (Context), the body around it (Harness), the library it can consult (RAG), the journal it keeps (Memory), the recipe cards in the backpack (Skills), the gear bolted on (Plugins & MCP), and where the data goes (Data). Number keys 1–9 (and 0) jump between them.

If you've shipped an agent into production, you already know the model is the cheap part — it's everything around it that decides whether the thing is safe, reliable, and worth running. This tab maps that "everything else," plus seven things worth committing to in the first week.

Investment posture

The harness, not the prompt

Conversational coaching is fragile, model-dependent, and doesn't scale. Durable capability lives in the harness around the agent — skills as code, deterministic guardrails, structured memory, identity, audit.

Engineering posture

Code beats prose

Anything that decides whether the agent can do something dangerous belongs in a hook, a schema, or a broker — not in a system prompt. Prompts can be argued with by an attacker; code cannot.

Operational posture

Bounded by default

Every run carries enforced limits and emits a machine-readable termination code. Every action passes through deterministic gates. Logs forward to a central SIEM. None of it is optional.

Seven commitments for week one

Each small enough to start before lunch; each foundational enough that everything else rests on it.

1 · Reviewable instructions

AGENTS.md + secret scanner

Make AGENTS.md the canonical instruction file. Wire gitleaks plus a small PII regex into pre-commit. Conversational coaching becomes a reviewable artifact, and the most common data leak — a real PII row pasted as an "example" — gets caught at commit.

2 · Hard limits

Step cap · cost ceiling · timeout

Every run carries enforced limits and emits a why_stopped code on termination. The cheapest insurance against the autonomous-loop failure mode — pays for itself the first time it fires.

3 · Lethal trifecta

Never combine private + untrusted + outbound

A deploy-checklist question. Refuse to deploy any path that combines private-data access, untrusted-content ingress, and outbound communication. Break at least one leg per task.

4 · Hook layer

Pre-execution tool hooks

A 50-line PreToolUse hook that blocks rm -rf, writes outside the workspace, .. path traversal, git push --force, and curl to non-allowlisted hosts. The harness becomes the enforcement boundary.

5 · Memory isolation

Per-user, per-org keys

Every persisted memory write keyed by (user_id, org_id, session_id). Harness-level assertion that read keys match the active principal. Closes the cross-user-leak class of bug.

6 · Audit + SIEM

Logs in one place

Pick an OTel GenAI span shape; instrument one agent end-to-end; forward to the existing SIEM. Without this, every other practice is unverifiable and every incident becomes archaeology.

7 · Injection regression

AgentDojo + 10 internal scenarios

Stand up AgentDojo against one production-shaped agent; freeze a 10-scenario internal addendum; block PRs that drop the score. Injection resistance silently regresses on every prompt edit otherwise.

Models

A "model" is the brain. Different brains have different sizes, speeds, and costs. You pick the right brain for the job.

Where the brains come from

Above is one company's lineup. There are several major sources — each with its own flavor.

Hosted by Anthropic Hosted by OpenAI Self-hosted on your hardware Router / aggregator
Same family, different sizes

Pick the right brain

Don't use a brain surgeon to read your mail. A small model answers quickly and cheaply; a large one reasons through hard problems. Most workflows mix both.

Many makers

Not just one company

Anthropic (Claude), OpenAI (GPT), Google (Gemini), Meta (Llama), and local open-source models all exist. They behave differently — like authors with different writing styles.

Multimodal

Words aren't all

Modern models also see images, hear audio, and read documents. The brain is the same; it just has more senses wired in.

Thinking — models that reason before they answer

Some models "think out loud" before responding. They generate a private chain of reasoning — sometimes visible to you, sometimes hidden — working through the problem step by step, then write the final answer. Slower and more expensive, but much better at hard problems.

When it pays off

Hard problems with chained steps

Reasoning models are worth the cost on problems where multiple steps have to chain together cleanly: complex math, multi-hop logic, code that needs to handle edge cases, planning under constraints. On simple Q&A or short content, they're slower and pricier for no real win.

The price

5–10× slower, 5–20× the bill

Reasoning models run noticeably slower — sometimes minutes per response — and the provider bills for the invisible thinking tokens too, often 5–20× the visible output. A reasoning call on a hard problem can land at $5–50 per request.

Real examples

Same trick, different flavors

OpenAI's o-series (o3, o4) emit thinking before answering. Anthropic's Claude has extended thinking mode. Google's Gemini has deep-thinking modes. All share the same trick: spend more tokens thinking, get a more accurate answer.

The takeaway

A model is rented intelligence. You pay per word in and per word out. Bigger model = smarter, slower, more expensive. Reasoning models add a second dial: spend more on thinking, get a better answer. Smart product design uses the cheapest model that gets the job right — and reaches for reasoning only when the problem needs it.

Model choice is a routing problem and a versioning problem. Get both right and the cost graph behaves; get either wrong and you'll find out the day a provider rolls a "compatible" update.

Version pinning

Pin specific versions, not floating tags

Providers ship "compatible" updates that shift behavior under you, and your evals only catch what they're run against. Pin to a specific model fingerprint and run the eval suite on every version bump as a CI gate.

Tiered routing

Small for routing, large for reasoning

Use a small/cheap model for classification, intent detection, and most steps. Reserve the flagship for genuinely hard reasoning. Paired with prompt caching, this typically cuts per-task spend by 50–90% before any other optimization.

Prompt-as-config

Versioned, paired to model

Treat the system prompt and skill bodies as versioned configuration: semver tags, changelogs, deprecation windows, and a compat matrix to model versions. Rollback should never be a guessing game.

The flagship model is rarely the right answer. The right answer is a routing layer that picks the cheapest model that finishes the task, paired to a versioned prompt, paired to a pinned model fingerprint. That's where the cost discipline lives.

Tokens

A token is a chunk of text — usually a whole word, sometimes a piece of one. It's the unit of measurement for almost everything that matters: how fast a model is, how much fits in the context window, and what each request costs.

The unit

Words, usually — sometimes pieces

Common words map to one token each ("the" → 1). Rare or compound words split into pieces: "tokenization" → 2 tokens, "antidisestablishmentarianism" → 7. Punctuation and spaces count too.

Two sides of the bill

Tokens in, tokens out

Every request has two prices: tokens in (what you send the model) and tokens out (what it writes back). Output is typically 3–5× more expensive than input — generating is harder than reading.

Scale check

1 million tokens ≈ 1,500 pages

A long memo: ~1K tokens. A novel chapter: 5–10K. A whole paperback: ~100K. An encyclopedia: 10M+. When a model advertises "200K context," that's roughly 300 pages it can hold at once.

What it costs

Prices vary wildly — even within one provider. Below: per-million-token pricing for representative models, with concrete examples of what it costs to push a 300-page book through each.

Tier matters more than maker

Pick the right tier first

Within any provider, the small tier is 10–50× cheaper than the flagship. Most production workflows split jobs across tiers — small models for routing, classification, and easy work; big models only for the hard reasoning. Most of the cost lives in routing decisions, not model choice.

Where the bill lands

Output dominates the cost

Apps usually send much more input than they get back — but because each output token costs 3–5× more, the bill often splits closer to 50/50. Worth optimizing both: trim what you send, and tell the model to be concise.

Caching — paying less when nothing changes

Reading a long prompt is expensive and slow. So providers cache the work they did on the steady parts — your system prompt, early conversation, long reference documents — and charge a fraction of the usual price when those parts are unchanged on the next call. You still pay; you just pay much less. The catch: caches don't last forever, and different providers run different stopwatches.

What gets cached

Only the prefix

Just the stable run of text at the start of your prompt — system prompt, early conversation, reference documents. The model's reply, your next question, and anything that changes flows fresh through every time.

Why it matters

Cheaper and faster

A cache hit costs roughly 10–50% of a cache miss and starts streaming back in a fraction of the latency. On long contexts — say a 100-page document the agent keeps consulting — the savings change what's economically possible.

Where it goes wrong: if your harness reshuffles tools or memories at the start of each turn, you blow the cache every time and pay full price. Stable order is everything.

What kills it

Time, or any edit to the prefix

Two things invalidate a cache: the clock running out (the bar above), or any change to the cached text. Adding one word to your system prompt forces a full re-read from byte one.

The takeaway

Tokens are the unit of currency in AI. Everything you care about — speed, cost, what fits in the context window — is measured in them. The cheapest performance win in most agents isn't paying for a smarter model; it's sending fewer tokens, and keeping the prefix steady so caching can work.

Tokens are signal. Cost-per-task, cache-hit rate, and the ratio of input to output tell you whether your agent is healthy long before any eval does.

The right denominator

Cost per completed task

Raw token counts are noise without a task denominator. "Tokens per day" can fall while completed tasks fall faster — a worse-but-cheaper agent. Always normalize by completed tasks before drawing conclusions.

Before scaling

Cost-forecast the canary

Before ramping an agent from 10% to 100% of traffic, model token spend, downstream API quotas, and inference rate limits at projected concurrency. The team that skips this learns about it from finance, not from a dashboard.

Attribution

Token accounting per agent, user, tool

Tag every spend with the agent, principal, and tool. When the bill triples month-over-month, someone needs to be able to answer which agent or workflow drove it — within minutes, not days.

Cache discipline

Stable prefix wins

Cache breakpoints belong at the end of stable content (system prompt, skill bundle, tool definitions). Any reshuffle invalidates everything after it. Often the single largest cost lever available before any architectural change.

Output trim

Tell the model to be concise

Output is 3–5× the price of input. A two-line system instruction to "answer in ≤300 words unless asked for more" can change the bill more than any model swap.

Anomaly alerts

Per-task budget alarms

Every agent run carries a soft per-task budget; runs that blow through it alert immediately. Without this, the $4,200-Saturday is something you discover Tuesday morning.

Context

A model has no memory of yesterday. Every time you talk to it, you hand it a stack of paper called "context." That stack has a maximum size — and reading a thick stack gets sloppy near the middle.

Context rot performance degrades as the context fills up

Below ~50% fullness the model stays sharp. Cross that line and the drop is steep — by 70% you're getting noticeably slower, less reliable answers, and near 100% the model starts missing things outright. This is why "just dump everything in" stops working.

Compaction how agents handle long conversations

When the stack gets too full, the agent collapses old chunks into short summaries. You lose some detail, but the conversation can keep going indefinitely.

The takeaway

The model is a goldfish that re-reads its whole notebook every time you speak. Bigger notebook = slower, more expensive, and easier to lose your place. Good agents are careful about what they keep in the notebook.

Context is a budget. Spend it deliberately — what to load, what to keep, what to drop — or watch quality bend and cost climb.

Budget the spend

Per-task context budget

Treat tokens added to context as a cost, not a benefit. Budget context length explicitly per task and enforce a watchdog. "Adding more context" is a regression unless you can name what improved.

Pull, don't push

Just-in-time context loading

Agents hold lightweight references (file paths, query handles, URLs) and fetch on demand. Eager retrieval is the exception, justified per agent. Stuffing the policy manual into context "in case" is the default failure mode.

Long-horizon hygiene

Declared compaction strategy

Any agent running beyond ~20 turns or ~100K tokens declares its summarizer prompt, what gets dropped, and what gets pinned (original task, success criteria). Without this, the agent forgets its plan around turn 80 and starts inventing requirements.

Watchdog

Auto-summarize or fail fast

When context utilization crosses a threshold (often ~70%), the harness either summarizes or terminates with why_stopped: context_overflow. Prevents the "context suicide" pattern where an oversized tool response drops the original task.

Continuous test

Context-rot smoke test

Replay representative tasks with padded context (50K, 200K, 500K of distractors) and verify quality doesn't degrade past a threshold. An agent that works at 20K and fails subtly at 200K is the kind of regression production catches for you.

Sub-agent offload

Delegate the noisy work

Any task expected to produce more than ~5K tokens of intermediate output goes to a sub-agent with isolated context. The main agent gets back a summary, not the raw search-result dump.

Context is the only resource the agent and the bill both compete for. The discipline is to treat it like a budget — measured, allocated, pruned, watch-dogged — instead of a place to dump anything that might help.

Harness

A bare model only takes text in and puts text out. The harness is the scaffolding around the model — the part that holds the conversation, runs tools on the model's behalf, asks for permission, and decides what the model gets to see on every turn. It's the difference between a brain in a jar and something you can actually drive.

It runs the loop

The model speaks once per turn

The model doesn't "stay running." Every turn, the harness packages a fresh prompt, sends it, reads the reply, and decides whether to loop again. Without a harness, there's no agent — just one isolated reply.

It runs the tools

The model can't press buttons

When the model says "please edit this file" or "please search the web," it's writing a request — the harness is what actually does it, after checking with you if needed. Tools live in the harness, not in the model.

It curates the view

It decides what the model sees

Every turn, the harness picks which memories to load, which files to include, how much history to keep, and where to spend the context budget. Different harnesses make different choices — that's most of why they feel different.

What "assemble" actually means

Every turn, the harness pulls each of these pieces from its own source and stacks them into a single prompt before handing it to the model. This is the same context window we saw in the previous tab — now from the harness's side: it's the harness's job to build this on every turn.

Subagents — when the agent sends a helper

Sometimes a job is too big or too messy to do in one head. A capable harness lets the main agent spawn a smaller helper — a subagent — to handle a piece of the work in its own private context, then return just a short summary. The mess stays downstairs.

Context hygiene

The mess stays downstairs

Whatever the subagent reads — 200 files, a wall of search results, a long log — lives only in its context window. The main agent gets back a clean summary and never has to wade through the raw material. When the subagent finishes, that context is thrown away.

Parallel work

Many heads at once

Independent tasks can run as separate subagents at the same time. "Search these five places in parallel" finishes in roughly the time of one search, not five — the harness juggles them and collects the summaries.

Specialization

Different helpers, different jobs

A subagent can have its own instructions and a narrower toolset — a researcher, a code reviewer, a verifier. The main agent picks the right specialist for each piece of work, like a manager handing tasks to people with sharper focus.

Real harnesses, side by side

The same model behaves very differently depending on which harness is wrapped around it.

Claude Code

Terminal-first, code-shaped

Anthropic's CLI harness. Lives in your terminal, edits files, runs commands, asks permission for risky operations, manages git. Built for shipping code. This explainer was built with it.

Cursor · Windsurf · Continue

Bolted into the editor

Harnesses that live inside a code editor. Same model under the hood, but the harness sees your open files, your cursor, your project structure — and slots its suggestions directly into the editor.

ChatGPT · Claude.ai

Chat-app harnesses

The web and mobile apps. Tuned for conversation: rich formatting, images, file uploads, voice. Fewer raw "do things in the world" tools than developer harnesses — by design.

OpenClaw · custom builds

Roll your own

Open-source harnesses you can self-host, or fully custom ones built on a vendor SDK. More control and privacy, but every feature — permissions, memory, hooks, tools — is yours to design and maintain.

The takeaway

A model on its own is a brain in a jar — it can write but it can't do. The harness gives it hands, eyes, a steering wheel, and a sense of where it's been. The same model in two different harnesses is, practically speaking, two different products.

Guardrails live in code, not in prompts. Every action passes through deterministic gates; the model is never the last line of defense. This is the layer that decides whether a prompt-injected document can do real damage.

why_stopped codes on every termination
Gate 1 · Authorization

The harness gates every call

Tool-call authorization happens in the harness, not in the model. Relying on the model to "know not to" is the magic-black-box failure mode this whole discipline exists to fix. "I told it not to" doesn't survive a prompt-injected document.

Gate 2 · Schema

Validate every argument

Declare and enforce a schema on every tool's arguments. Reject calls with unexpected fields, untyped values, or pattern-matched dangerous values: DROP TABLE, .. traversal, control characters, unallowlisted URLs. Trust nothing the model wrote.

Gate 3 · Hook

Pre-execution behavioral block list

Every serious harness supports PreToolUse hooks that fire around every tool call and can block on exit code. Maintain a versioned, peer-reviewed library of "if the agent tries X, hard block."

Gate 4 · Sandbox

Filesystem, network, kernel isolation

Treat container-only isolation as insufficient for untrusted code. For code-executing agents, require Firecracker, Kata, or vendor microVM (E2B, Modal). A Docker container that shares the host kernel is one malicious npm postinstall script away from breakout.

Gate 5 · Human

Typed approval for irreversible writes

Irreversible writes (account changes, payment actions, partner-data updates) hit explicit interrupt points with typed approval payloads. Not "Are you sure? (yes/no)" — a structured object an auditor can read six months later.

Encircling all gates

Hard caps, kill switch, why_stopped codes

Every run carries enforced step / cost / wall-clock limits and emits a why_stopped code on termination. The kill switch halts in-flight calls, not "next turn." This is how the $4,200 SSH loop becomes a $25 incident.

The single most important deploy check

If you add nothing else from this tab, add this.

Lethal-trifecta gating

Refuse private-data + untrusted-content + outbound on one path

Most exfiltration paths collapse if a single execution path cannot have all three simultaneously. A "helpful research agent" that reads internal docs (private), browses the open web (untrusted), and can email anyone (outbound) is the canonical example of an agent that will exfiltrate to the first attacker who notices. Split it: one agent reads but cannot send, another sends but cannot read.

RAG

RAG stands for Retrieval-Augmented Generation. Before answering, the agent searches a pile of your private documents for the most relevant chunks, then hands those chunks to the model along with your question. It's how an agent stays grounded in information it wasn't trained on — without dumping a whole knowledge base into context every time.

The win

Search by meaning, not keywords

Vector search finds chunks that are about the same thing, not chunks that share words. "How do I get my money back?" matches "refund policy" even though no word is shared. Old-school keyword search would miss this entirely.

Why it scales

Only what's needed

You might have 10,000 documents. RAG sends maybe 5 short chunks per question. The model never sees the rest. The knowledge base can grow without growing the context budget — the opposite of "just paste it all in."

Why it's flexible

Fresh, not frozen

The vector database is yours — update it any time. New policy doc? Re-index it and the agent answers using the new version the next minute. The model itself never changes; what it reads changes. No retraining required.

What's a vector database?

A vector database stores the "fingerprints" of your documents. Each chunk gets converted to a list of numbers (an embedding) that captures its meaning. Two chunks about the same topic have similar fingerprints — even if they share no words. The database is built to find nearest neighbors fast, across millions of fingerprints.

Fingerprints

Embeddings capture meaning

Each chunk of text gets turned into a list of ~1,000 numbers. The numbers themselves are nonsense to humans, but they place the chunk in a "semantic space" where similar things sit close together. This is what makes meaning-search possible.

One job, very fast

Built for similarity lookup

A vector database stores millions of these fingerprints and finds nearest neighbors in milliseconds — even across a corpus too big to scan linearly. That's the one thing it's optimized for.

Many flavors

Managed or DIY

Pinecone, Weaviate, Qdrant, Chroma — managed services with their own clouds. Postgres + pgvector — DIY on infrastructure you already run. Choice usually comes down to managed convenience vs hosting it yourself for privacy or cost.

The takeaway

RAG turns "the model doesn't know our stuff" into "the model can read up before answering." It's the standard pattern for grounding agents in private data, and it scales: the knowledge base can grow without growing the context window. The model never learns your data — it just gets handed the right pages right before it speaks.

Retrieved content is untrusted input. Treat it as data, not instructions — or the first poisoned document rewrites the agent's goals while looking exactly like a normal answer.

Treat retrieval as untrusted

Spotlighting on every channel

Datamark or encode RAG hits, web results, and email content at the boundary so the model treats them as data, not instructions. Retrieved text and user instructions arriving in identical formatting is how indirect prompt injection wins.

Cite or abstain

Sentence-level source attribution

Require sentence-or-passage citations. Document-level is too coarse to verify. If a claim has no retrieval source, the answer is "I don't know" or a structured deferral — never a confident invention.

Pick the right mode

Long-context vs RAG router

Document per agent which mode is in use and the corpus characteristics that justify it. Stuffing a 1M-token corpus into context every call because "the model can handle it" pays 1,250× the cost of RAG for ~60% of the recall.

Dual-LLM separation

Quarantine untrusted content

For high-stakes tool-using paths, an untrusted-content reader returns opaque references; the tool-invoking model never reads tainted text directly. CaMeL / Dual-LLM pattern. The first level of "actually fixing" prompt injection.

Test continuously

Injection regression suite

AgentDojo + AgentHarm + a frozen set of 10–30 internal scenarios run on every prompt or tool-schema change. A "small" prompt tweak ships on Friday; on Monday the customer-support reader is exfiltrating data. The suite catches it before merge.

Re-rank, don't trust

Adversarial filtering on top-k

After retrieval, re-rank by source provenance (internal docs > vendor docs > web), and drop hits from low-trust sources for high-stakes prompts. Constitutional classifiers reduce attack success but don't eliminate it — pair every classifier with at least one architectural control.

The model can't tell "instructions for you" from "content to consider" unless the harness marks them differently. Spotlight at the boundary, cite at the sentence, abstain when sourceless, separate trust contexts for the high-stakes paths. Then test it. Then test it again.

Memory

If the model is a goldfish, memory is the notebook it consults before every conversation. AGENTS.md / CLAUDE.md are the house rules pinned to the wall.

Memory (per user)

Travels with you

Notes the agent writes about you: preferences, who you are, things you've asked it to remember. Persists across every conversation. Lives in your account, not the project.

Where it goes wrong: retrieval is fuzzy — the agent picks the note that sounds closest to your question, not necessarily the right one. Stale notes don't expire on their own. And every loaded note eats context budget — past a few dozen, the truly useful ones get harder to spot.

AGENTS.md (per project)

Travels with the codebase

A markdown file checked into the repo. Anyone who works on that project — human or agent — gets the same house rules: how to deploy, what's forbidden, where things live.

Where it goes wrong: rules accumulate without pruning, leading to contradictions ("always X" written one month, "never X" written the next). And every rule rides along on every turn — a wall of rules leaves less room to think, even on tasks they don't apply to.

The takeaway

Memory is what makes an agent feel like it knows you — but every memory is a bet that the fact will stay true and that the agent will retrieve it correctly. Curate sparingly: a small, fresh set beats a sprawling, stale one. Prune like a garden, not a hoarder's attic.

Memory is the most failure-prone surface in agentic systems. Explicit scope, structured schema, and temporal validity are what stop it from becoming a leak channel.

Scope by principal

Composite keys at every write

Every persisted memory keyed by (user_id, org_id, session_id). The harness asserts read keys match the active principal. Cross-user contamination via similarity hit or cache leak is the breach scenario most likely to become a public incident.

Schema, not prose

Every entry carries metadata

Provenance, timestamp, validity window, PII classification. Free-text dumps into memory are forbidden. An entry that says "user prefers email" with no provenance is something the agent will cite as fact a year later, when it isn't true anymore.

Time-aware

Supersede, don't delete

Facts have validity windows. When a fact changes, the new entry supersedes the old; the old is preserved with an expired window. "What did the agent know on date X" becomes a reconstructable question instead of a guessing game.

Taxonomy

Working, episodic, semantic, procedural

Classify every persisted memory by class and name the consolidation pathway. Throwing transient session state and durable facts into one undifferentiated vector store means the agent confidently cites last week's stale assumption as fact.

Bound the instruction files

No secrets, PII, or contract data in AGENTS.md

AGENTS.md / CLAUDE.md are read by every invocation and checked into source. Forbidden surface for anything sensitive. A real user email pasted as an "example" is now in every session log forever.

Forget on demand

Right-to-be-forgotten flows

Memory deletion has to actually delete — across the vector store, the structured store, and any cache. If your platform commitments include user data deletion, this needs to be a tested, auditable workflow, not a hope.

The takeaway

"I'll just have it remember" is the agentic equivalent of a sticky note on a server: it works until it doesn't, and when it doesn't, it leaks. The discipline is to make memory a schema, not a sticky note — keys, fields, provenance, validity, classification.

Skills

A skill is a recipe card the agent pulls off the shelf when it sees a job that matches. Skills let an agent do specialized work without bloating every conversation with instructions it doesn't need.

On-demand

Loaded just-in-time

Skills sit on a shelf until they match. Hundreds of skills can exist without slowing the agent down — only the relevant one comes off the shelf.

Where it goes wrong: the matching is keyword-based. A "when to use" that's too vague ("use when working on code") fires for everything; too narrow ("pytest -k on Tuesday") fires for nothing. From your side, both look identical — the skill behaves inconsistently.

Markdown, not code

Anyone can write one

A skill is a plain markdown file with a name, a "when to use" description, and steps. No programming required.

Where it goes wrong: there's no compiler to catch a sloppy "when to use," and no warning if two skills overlap on the same trigger. The agent silently picks one — usually the first — and the others go unused. You only notice when output gets weird.

Shareable

Bottle your expertise

Have a procedure that always works? Write it as a skill once, and every agent on the team uses it the same way every time.

Where it goes wrong: skills age out. A recipe written for last year's tooling still triggers, but the steps inside no longer reflect how the system actually works. The agent confidently runs an obsolete recipe. Prune like any other code.

The takeaway

Skills turn one-off prompts into reusable procedures, but the win comes from a small library of sharp, well-described skills — not a sprawling shelf of half-overlapping ones. The agent can only run a skill if it knows when to reach for it; if it can't tell two apart, you get inconsistency.

Skills are code: source-controlled, peer-reviewed, signed, sunset on a calendar. Conversational coaching does not compose across users, teams, or model swaps.

Treat as code

Skills are engineering artifacts

Source-controlled, peer-reviewed, tested, versioned. "Training the agent in chat" is not a thing — the moment the conversation ends, the capability evaporates. A skill is the artifact; the prompt is glue.

Lean by default

Progressive-disclosure SKILL.md

Trigger criteria in frontmatter; body lean; bulk reference in linked files. Context cost stays roughly constant as the skill library grows. Dumping the full body into the system prompt means paying for hundreds of skills every invocation doesn't use.

Where things live

Skill vs MCP vs prompt

Methodology goes in a skill. Connectivity goes in an MCP server. Deployment-specific behavior goes in the system prompt. Three places, three responsibilities — and crucially, nothing lives in two places at once.

Distribution

Registry + scopes + sunset

Define scopes (private / org / public) with explicit promotion criteria. Run an internal registry with vetting, signing, and provenance tracking. Require retirement criteria — useful private skills get DM'd around and become load-bearing across teams without ever being reviewed.

Discovery

Search before you write

Give practitioners a search surface for the registry (frontmatter tags, owner, last-reviewed date). Without discovery, teams write a fourth duplicate. Without sunset, the registry calcifies. Both are common; both are fixable in a week.

Supply chain

Pin by commit SHA, treat unsigned as untrusted

Mirror third-party skills and MCP servers into an internal registry. Pin by commit SHA. Treat unsigned artifacts as untrusted code (sandbox, no secrets, no egress by default). Installing from a public marketplace by name is the canonical supply-chain attack vector.

The takeaway

The difference between a one-off prompt fragment and a durable capability is the same as the difference between a sticky note and a function in a versioned package. Write the skill. Sign it. Mirror it. Sunset it. The agent's library should look like any other code library.

Plugins

A plugin is a sealed box that ships tools, hooks, and skills together. Install the box, get all three. Uninstall, and they're gone cleanly.

🔧 Tools

New verbs

Things the agent can do — call APIs, edit files, query a database. Each tool is a function the agent picks up like a new appendage.

🪝 Hooks

Tripwires

Code that fires before or after specific events. "Before any merge, ping the channel." "After every file edit, run the linter." Automatic, not asked for.

📐 Skills

Playbooks

The procedures that combine the tools and the hooks into something useful end-to-end. Plugins ship skills so installing the plugin gives you the workflow, not just raw pieces.

The takeaway

Plugins are how an agent grows. A vanilla agent talks. With plugins, it can file tickets, deploy code, draft emails, query your data warehouse, post to Slack — and it picks up house rules and safety checks along with the new abilities.

Plugins extend the harness; they don't bypass it. Supply-chain hygiene is the difference between a contained extension and a backdoor someone else's package is using to ship code on your laptop.

Extend, don't fork

Plugin-based harness extension

Treat the hook system as a first-class plugin surface. Internal teams ship enforcement controls (DLP, behavioral patterns, custom approvals, audit forwarders) as versioned plugins. Forking the harness to add controls means inheriting every upstream security patch by hand, forever.

Verify what you install

Slopsquatting defense

Require package-existence, age, and maintainer-reputation checks (or lockfile-only mode) before any agent-initiated npm install, pip install, uv add. About 20% of LLM-recommended packages do not exist — attackers register the hallucinated names and wait.

Refuse the easy mode

Yolo-flag ban in CI & on workstations

Detect and block --dangerously-skip-permissions, --yolo, --trust-all-tools in postinstall scripts, CI runners, and pre-commit hooks. The first compromised dependency turns "fast personal config" into "full agent autonomy on the developer's laptop."

Confirm the gates still gate

Permission-rule enforcement test

Automated test in CI that the harness's deny rules actually block in the current version. Re-run on every harness upgrade. Upstreams ship "compatible" updates that silently weaken deny-list semantics; you find out three weeks later when an agent does something it shouldn't have.

Run untrusted code as untrusted

MicroVM floor for code-executing agents

Code-executing agents run inside Firecracker, Kata, E2B, or Modal — not a shared-kernel container. A malicious npm postinstall script is one container escape away from your secrets otherwise.

Browser-touching agents

Browser-session ephemerality

Each browser-agent task runs in a fresh VM with the browser binary destroyed after. No cross-task profile reuse. A poisoned page from one task drops a cookie that persists into another otherwise.

The takeaway

The agent is a code-executing platform now. Treat plugin and dependency hygiene the same way you'd treat any production code path: pin versions, verify maintainers, sandbox untrusted code, never let convenience flags survive into shared environments.

MCP Servers

MCP stands for Model Context Protocol — an open standard that lets any agent talk to any service through a single shared plug. Think USB for AI tools. Before USB, every peripheral had its own custom cable; after USB, one socket served everything. MCP is the same bet for AI.

Standard plug

One protocol, any harness

Write the connector once, every MCP-aware agent uses it. A GitHub server works in Claude Code, in Cursor, in your own Python script — same interface, no rewrites per harness.

Three primitives

Tools, resources, and prompts

An MCP server can expose three things: tools (actions to take), resources (data the agent can read), and prompts (ready-made templates a user can pick). Most servers focus on tools, but the protocol covers more.

Runs where you want it

Self-hostable by default

MCP servers are separate processes you start yourself. For sensitive systems — your database, your inbox, your internal wiki — the server can live entirely inside your network. Nothing leaves until you decide it should.

Plugins vs MCP servers — close cousins, not the same

Both extend what an agent can do. They package it differently.

Plugins

Bundles, harness-specific

Tools + hooks + skills packaged together for one specific harness. Runs inside the harness process. Rich: can intercept events, ship workflows, register skills. Not portable — a Claude Code plugin won't run in Cursor or Continue without a rewrite.

MCP servers

Connectors, harness-agnostic

Tools (plus resources and prompts) exposed over a standard wire protocol. Runs as a separate process, talked to by the harness over stdio or HTTP. Narrower scope, but fully portable: the same server plugs into any MCP-aware harness.

The takeaway

MCP is to AI tools what USB became to peripherals: a boring, universal plug. Once a service has an MCP server, every MCP-aware agent — no matter who built it — can talk to it. The boring part is exactly why it works.

MCP discipline is toolset gating, tool budgets, and trace propagation. Without them, MCP is just a wider attack surface with prettier documentation.

Gate the surface

Read-only / write / admin toolsets

Group tools into enable/disable surfaces and audit which gate was active per call. A read-only research agent with the delete tool loaded "just in case" is the exact configuration prompt-injected documents are written to find.

Budget tools

Hard ceiling on loaded tools

Set by what your evals show degrades selection accuracy. Current heuristics put this around a few dozen tools, but the number ages with the model. Above the ceiling, require dynamic tool retrieval — Tool2Vec / Tool-RAG / Tool-to-Agent indexes.

Shape for workflows

Custom MCP servers, workflow-shaped

Wrap internal tools as MCP servers with their own auth, tests, versioning. Workflow-shaped tools, not API-shaped — an MCP server that mirrors every endpoint of a REST API gives the agent 200 tools and no idea which to use.

Auth like an API

OAuth 2.1 + RFC 8707 Resource Indicators

On the integration boundary, full OAuth 2.1 with Resource Indicators. Static bearer tokens are a smell — they grant blanket access, leak into logs, and don't expire. Resource indicators scope tokens to specific MCP servers.

Trace across

W3C traceparent in MCP _meta

Inject traceparent into MCP request _meta so client and server share a trace. Without it, the agent trace ends at the MCP boundary; you can see the call left, you can't see what happened on the server side.

Pin the supply chain

Mirror, sign, pin by SHA

Treat MCP servers from public marketplaces as untrusted code. Mirror to an internal registry. Pin by commit SHA. Unsigned servers run sandboxed, no secrets, no egress. The MCP ecosystem is young; the attacks are not.

The takeaway

MCP standardizes the wire format, not the discipline around it. Gate the toolset, budget the count, scope the tokens, propagate the traces, pin the supply chain. The standard is boring on purpose; the work is in what you build around it.

Data

Where does your prompt go after you send it? What gets logged? Will your conversation train the next model version? The answers depend on the provider, the plan, and the harness — and "depends" is often the most honest answer.

The training question

"Is my data used to train future models?" is the first question most people ask. The answer depends sharply on how you're accessing the model.

Developer API

Usually opt-out by default

For all major API providers (Anthropic, OpenAI, Google), API traffic is not used to train future models by default. This is the contractual baseline for paid developer access. Logs may still exist for safety review and abuse detection — but those don't feed back into training.

Consumer chat apps

Often opt-in by default

The free and lower-tier consumer apps (ChatGPT free, Gemini free, etc.) frequently use your conversations to improve future models — unless you go into settings and turn it off. Some paid tiers flip this. Always read the privacy settings before pasting sensitive content.

Enterprise plans

Contractually opt-out

Enterprise and business tiers add legal guarantees: no training, often shorter or zero log retention, sometimes private deployments. This is what regulated industries use. The protection lives in the contract, not the technology.

Self-hosted

N/A — there's no provider

When you run an open-source model on your own hardware, there's no provider hop to worry about. Your prompts never leave your network. But you also take on hardware, performance, and maintenance costs — and most open models lag the flagship hosted ones.

What self-hosting actually buys you

Self-hosting is the loudest privacy answer, but it's not a clean win. Here's what it does and doesn't do.

What it eliminates

The provider hop

Your prompts never reach a third party's servers. No external logging, no risk of training, no ToS to read. For sensitive data (medical, legal, regulated), this is often the only acceptable answer.

What it doesn't eliminate

Everything else

The harness still runs somewhere. The network still carries traffic. The MCP servers your agent talks to are still doing their thing. If any of those are hosted elsewhere, you've only moved the boundary — you haven't closed it.

What it costs

Real money & real work

Hardware (GPUs aren't cheap), electricity, cooling, model updates, performance gap vs hosted flagships, and the ongoing maintenance of running your own infrastructure. Worth it for some workloads — not all.

The takeaway

Your data takes a journey, and the privacy story lives in the defaults and contracts more than in the technology. For non-sensitive prompts, the defaults are usually fine. For sensitive ones, read the ToS before sending anything — and consider self-hosting if the answer is unclear or unacceptable. "Where does my data go?" is always a fair question to ask.

Identity is the most load-bearing layer; audit is what turns "the agent did it" into something investigable. This tab is the boring, foundational stuff that lets every other practice hold.

Identity & credentials

Who is calling, on whose behalf, with what credentials, for how long.

Never raw secrets

Secrets-broker pattern

Agents call get_token(scope, ttl); the broker returns a short-lived token bound to the principal and scope. Logs capture issuance, not the token. The API key never appears in a system prompt, transcript, or trace.

Time-bounded grants

Capability tokens with TTL

Scope every grant to one task, one resource, one expiry. Minutes for sensitive flows, hours for routine, never "approve once, use forever." The agent approved last quarter for a one-time migration should not still have the access today.

Workload identity

SPIFFE/SPIRE for agents

Every agent process carries an attested cryptographic identity (X.509-SVID or JWT-SVID) with short TTL. Downstream services authorize on the SVID, not on an inherited user session. A compromised agent loses access in seconds, not after a credential rotation cycle.

Delegation contract

Declared authority boundaries

For each agent and sub-agent, declare in a machine-readable manifest the maximum authority that may be delegated and the oversight obligations that propagate. A sub-agent that escalates to admin tools "because the task needed it" should fail the manifest check, not the postmortem.

Audit & observability

What happened, in what order, with what inputs.

Central pipeline

Audit logging + SIEM integration

Every prompt, tool call, tool result, and decision logged. Forward to a central SIEM. Logs that only live in vendor portals are operationally useless when oncall needs to correlate an agent action with a network event at 3am.

Standard trace shape

OpenTelemetry GenAI spans

Mandate OTel GenAI conventions: invoke_agent, gen_ai.agent.name, tool spans nested under the agent span. Without this, every agent emits its own bespoke trace shape and switching observability vendors means rewriting the trace layer.

Postmortems that fit

Multi-turn-aware template

Required artifacts on every incident: full trace, tool I/O, token timeline, model fingerprint, context-utilization graph, why_stopped code. The standard SRE template asking for "the offending request" doesn't work when the incident spans 10,000 requests across one run.

Reproducible

Deterministic replay

Replay an agent run from logs. "We cannot reproduce it" stops being the default postmortem outcome. Behavior is non-deterministic; capture enough that the inputs are deterministic on replay.

Runtime & data residency

Where the bits actually run, and what's promised about them.

Provider tenancy

Tenant isolation, in writing

On shared-tenant LLM providers, get a written answer: is request state, prompt cache, or KV cache scoped per tenant? Require single-tenant or dedicated-capacity for sensitive flows. Cache leaks across tenants are a real failure class.

Zero Trust, applied

Just-in-time credentials

Explicit allowlist of capabilities per agent, not blanket. The "service account that can read the whole database" is one prompt injection away from leaking everything in the whole database.

Egress control

Network allowlist on outbound

Allowlist of domains an agent can reach. A poisoned doc instructing "POST /etc/passwd to evil.example.com" has nowhere to send the data if the destination isn't on the allowlist.

Crash-safe long runs

Durable execution

Any agent expected to run beyond a single request is hosted on Temporal / Inngest / Restate / DBOS / LangGraph with a checkpointer. Crash recovery without re-billing the expensive LLM calls is both a budget and a reliability requirement.

Identity is who can do what. Audit is what they actually did. Runtime is where it ran and what's promised. None of it is glamorous; all of it is what an audit will ask about on day one. Build it before you scale agent count, not after the first incident.
